2. new RedisStore(...)
new RedisStore({

RedisStore comes from:

import RedisStore from "rate-limit-redis";

It's an adapter between:

express-rate-limit
        ↕
      Redis

express-rate-limit doesn't directly know how your Redis client works, so RedisStore handles the storage logic.

3. sendCommand

This is probably the most confusing part:

sendCommand: async (...args: string[]) => {
  return redis.call(args[0], ...args.slice(1)) as Promise<any>;
},

The RedisStore needs to execute Redis commands.

For example, it might need to do something conceptually like:

GET some-key
INCR some-key
EXPIRE some-key 900

Your sendCommand function tells it:

"Whenever you need to execute a Redis command, use my redis client."

What does ...args mean?

Suppose RedisStore calls:

sendCommand("GET", "rate-limit:login:123.123.123.123")

Then:

args

contains:

[
  "GET",
  "rate-limit:login:123.123.123.123"
]

Then:

args[0]

is:

"GET"

And:

args.slice(1)

is:

[
  "rate-limit:login:123.123.123.123"
]

Therefore:

redis.call(args[0], ...args.slice(1))

becomes essentially:

redis.call(
  "GET",
  "rate-limit:login:123.123.123.123"
);

So this function is basically forwarding the Redis command.

4. Why async?
sendCommand: async (...args: string[]) => {

Redis operations are asynchronous.

Your application doesn't want to freeze while waiting for Redis.

Conceptually:

Node.js
   │
   ├── Send command → Redis
   │
   ├── Continue handling other work
   │
   └── Receive Redis result later
5. What does this mean?
as Promise<any>

You're telling TypeScript:

"Treat the result of this Redis operation as a Promise."

It's a TypeScript type assertion.

It's not doing anything to Redis itself.

6. prefix
prefix: "rate-limit:login",

This tells RedisStore to use a prefix for its Redis keys.

Think of Redis as a giant key-value store:

KEY                              VALUE

rate-limit:login:IP1              3
rate-limit:login:IP2              1
rate-limit:login:IP3              5

The prefix makes it clear that these keys belong to your login rate limiter.

You could have other rate limiters:

rate-limit:login:...
rate-limit:register:...
rate-limit:forgot-password:...
rate-limit:api:...

This keeps Redis organized.

You're creating a warning in your backend logs.

For example:

LOGIN_RATE_LIMIT_EXCEEDED {

This can help you identify suspicious activity.

8. req.ip
req.ip

This gives you the client's IP address as Express sees it.

For example:

192.168.1.20

The rate limiter generally uses this kind of client identifier to distinguish users/clients.

9. req.originalUrl
req.originalUrl

This tells you which URL was requested.

For example:

/api/auth/login

So your log tells you:

WHO?
↓

WHAT?
↓
